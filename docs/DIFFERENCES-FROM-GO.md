# Go CLIProxyAPI와 다른 점

> 이 문서에서 알 수 있는 것: horon-router가 Go 버전과 일부러 다르게 동작하는 부분, 그리고 horon-router가 추가한 라우팅 방식 하나.

horon-router가 어떤 기능을 제공할 때는 CLIProxyAPI의 커밋 `6fecc6e`와 똑같이 동작하는 것을 목표로 합니다. 이 문서는 일부러 다르게 동작하는 곳과, horon-router가 추가한 라우팅 방식 하나를 정리합니다. 아직 옮기지 않은 기능은 대신 [앞으로 추가될 기능](../README.md#upcoming-features)에 있습니다.

<a id="additions-in-horon-router"></a>
## horon-router가 추가한 것

- 라우팅 방식 `quota-failover`. 직접 켜면 같은 모델 이름이나 별칭을 제공하는 계정 중 사용량이 소진된 계정을 제외하고 다른 제공자로 전환합니다. Command Code, Devin, OpenCode Go의 사용량 조회와 Claude·Codex의 기존 관측을 사용하며 불명확한 사용량은 소진으로 취급하지 않습니다. Go에는 없는 방식이고 기존 선택 방식에는 조회를 추가하지 않습니다. 설정과 전환 경계는 [QUOTA-FAILOVER.md](QUOTA-FAILOVER.md)를 확인하십시오.

- 라우팅 방식 `soonest-reset`(별칭 `reset-first`). 실험적이고 직접 켜야 하는 기능입니다. 주간 사용 창이 가장 빨리 초기화되는 계정을 고릅니다. 그 계정이 쿨다운(잠시 쉬게 하는 시간)에 들어가거나 한도에 닿으면 다음 계정으로 넘어갑니다. 초기화 시간을 아직 모르는 계정에는 확인용 요청을 한 번 보냅니다. 한 계정에 묶인 대화는 그 계정에 그대로 남습니다. Go에는 `round-robin`, `weighted-round-robin`, `fill-first`만 있고, `soonest-reset`은 `round-robin`으로 읽습니다. 대시보드는 horon-router에 연결됐을 때만 이 방식을 보여 줍니다. 자세한 내용은 [MULTI-ACCOUNT.md](MULTI-ACCOUNT.md#routing-strategies)를 보십시오.
- API 문서 경로 세 개. Go에는 없는 `GET`(와 `HEAD`) `/openapi.json`, `/docs`, `/docs/assets/scalar.js`를 둡니다. `/openapi.json`은 서버가 아는 고정 경로를 담은 OpenAPI 3.1 명세이고, `/docs`는 그 명세를 보여 주는 Scalar 문서 화면이며, `/docs/assets/scalar.js`는 서버에 내장한 Scalar 자산입니다. 세 경로는 키 없이 열리지만 시험 요청은 기존 인증을 그대로 받습니다. 자세한 내용은 [OPENAPI.md](OPENAPI.md)를 보십시오.
- Codex 연결 재사용. 직접 켜야 하는 기능입니다. `oauth.providers.codex.chatgpt-keep-alive: true`를 설정하면 `chatgpt.com`용 Codex 클라이언트(Chrome TLS 지문을 씁니다)가 호스트마다 유휴 연결과 프록시(요청을 대신 전달해 주는 중간 서버)를 최대 2개까지 90초 동안 유지합니다. 그리고 나중에 오는 요청을 그 연결로 보냅니다. HTTP/2에서는 여러 요청을 한꺼번에 보냅니다. ClientHello, 요청 헤더, 프록시는 그대로이고, 연결이 프록시를 넘어가는 일은 없습니다. 기본값인 꺼짐 상태에서는 Go와 똑같이 동작합니다. 요청마다 전용 연결을 쓰고, 응답 본문과 함께 연결을 닫습니다(`helps/utls_client.go`). 이 설정은 설정을 다시 읽은 뒤 오는 요청부터 적용됩니다. Go는 이 키가 파일에 있어도 시작할 때 무시합니다. Go의 v8 관리 API로 설정을 고치면 이 키가 주석으로 옮겨집니다. 그래서 다시 horon-router로 돌아오면 설정이 꺼진 상태가 됩니다. Go의 v0 엔드포인트로 고치면 키가 유지됩니다. Go의 v8 API로 이 키를 설정하려 하면 거부됩니다. Go가 모르는 키는 모두 그렇습니다.
- `worker-threads`(`config.yaml`의 최상위 키). 요청을 처리하는 스레드 개수입니다. 기본값은 CPU 개수와 2 중 작은 값입니다. 자세한 내용은 [CONFIGURATION.md](CONFIGURATION.md#worker-threads)를 보십시오. Go는 스케줄러 크기를 CPU 개수로 정합니다. 이 키는 시작할 때 `-config` 파일(기본값 `./config.yaml`)에서 한 번만 읽습니다. 원격 저장소나 Home이 설정을 공급하기 전입니다. 저장소의 `config.yaml`이나 Home이 공급하는 설정에서는 아무 효과가 없습니다(로컬 `-config` 파일은 여전히 적용됩니다). 그런 환경에서는 대신 `TOKIO_WORKER_THREADS`를 설정합니다. Go는 이 키가 있어도 시작하고, v0 관리 API로 저장해도 값을 유지합니다. v8 설정 쓰기(`/v8/management/config` 아래의 PUT, PATCH, DELETE)는 이 키를 `# worker-threads: N` 주석으로 바꾸고, `unrecognized configuration section "worker-threads" commented out during v8 migration`을 로그에 남깁니다. 또 이 키가 있는 `PUT /v8/management/config.yaml`는 `unknown v8 configuration section worker-threads`로 답합니다. 하나의 config.yaml을 Go 서버와 함께 쓴다면 대신 `TOKIO_WORKER_THREADS`를 설정하십시오.

<a id="deliberate-differences"></a>
- `POST /v8/management/quota/fetch`. 대시보드는 `/v8/management`로 요청하므로 이 경로를 둡니다. Go의 v8 관리 API에는 없어 빈 본문이면 404입니다. horon-router는 v0 `POST /v0/management/quota/fetch`와 같은 본문·오류로 답합니다. 빈 객체 `{}`는 `400`과 `auth_index is required`입니다.
- Command Code 제공자(`command-code`). Go에는 없고 opencodex의 `command-code` 어댑터를 참고해 구현했습니다. 계정 키로 `https://api.commandcode.ai/alpha/generate`에 요청하고, 모든 클라이언트 형식을 OpenAI Chat으로 바꾼 뒤 이 주소의 본문으로 다시 만듭니다. 답은 NDJSON 스트림이며 OpenAI chat 청크로 되돌립니다. 로그인은 `-command-code-login`이나 대시보드의 Connect 화면에서 합니다. 브라우저 로그인, `~/.commandcode/auth.json`(Command Code CLI) 가져오기, API 키 붙여넣기를 지원하고 키는 `/alpha/whoami`로 확인한 뒤 `auth-dir`에 `command-code-<사용자 ID>.json`으로 저장합니다. 모델 목록과 추론 단계는 opencodex의 정적 표(2026-09-23 기준)이며 실제 서비스 카탈로그로 갱신하지 않습니다. 목록에 없는 모델도 요청은 보내지만 추론 단계는 보내지 않습니다. 남은 사용량은 대시보드의 Quotas 화면에서 조회합니다. 서버가 `/alpha/whoami`(팀 `orgId`), `/alpha/billing/credits`(5시간·주간 한도와 남은 크레딧), `/alpha/billing/subscriptions`와 `/alpha/usage/summary?since=`(결제 기간 전체 사용량)를 이어서 호출하고, 대시보드는 그 결과를 5시간·주간·전체 한도와 남은 크레딧으로 보여 줍니다. 서버가 백그라운드에서 자동으로 조회하지는 않습니다. 이미지·영상·`responses/compact`는 지원하지 않습니다. `x-session-id`는 요청의 세션 키에서 만들며, 작업 폴더와 git 상태를 보내는 `config`는 비워서 보냅니다. 실제 Command Code 서비스로는 검증하지 않았습니다.
- Nous Portal 제공자(`nous`). Go에는 없고 opencodex의 `nous` 로그인을 참고해 구현했습니다. 기기 코드 방식으로 로그인하고(`-nous-login`, 대시보드 Connect), 받은 접근 토큰(추론용 JWT)을 `https://inference-api.nousresearch.com/v1`에 OpenAI Chat 형식으로 보냅니다. Nous의 갱신 토큰은 한 번만 쓸 수 있어서, 갱신 요청이 서버에 닿은 뒤 실패하면 같은 토큰을 다시 보내지 않고 오류를 그대로 돌려줍니다. opencodex처럼 재시도 방지 기록을 디스크에 따로 남기지는 않으므로, 갱신 응답을 받고도 인증 파일 저장이 실패하면 세션이 폐기될 수 있습니다. 모델 목록은 opencodex의 기본 4개이고 계정별 실제 목록으로 갱신하지 않습니다. 실제 Nous 서비스로는 검증하지 않았습니다.
- GitHub Copilot 제공자(`github-copilot`). Go에는 없고 opencodex의 `github-copilot` 로그인을 참고한 비공식 연동입니다. VS Code의 공개 OAuth 클라이언트로 GitHub 기기 코드 로그인을 하고(`-github-copilot-login`, 대시보드 Connect), `copilot_internal`에서 단기 Copilot 토큰으로 바꿔 `*.githubcopilot.com`에 OpenAI Chat 형식으로 보냅니다. 토큰은 `*.githubcopilot.com` 주소로만 보내고 다른 주소는 무시합니다. GitHub이 이 경로를 막을 수 있습니다. Responses 형식만 받는 모델(`gpt-5.x`, `gpt-6.x`, `grok-4.x` 등)은 이 실행기가 Responses를 쓰지 않아 400으로 거절하며, 모델 목록에도 넣지 않았습니다. 실제 GitHub Copilot 서비스로는 검증하지 않았습니다.
- Google Antigravity 제공자(`antigravity`). Go 기준 커밋에는 이 실행기가 없고, opencodex의 Cloud Code Assist 연동을 참고해 구현했습니다. README의 "Google Antigravity 계정" 미지원 항목은 이 구현으로 해소됩니다. Google OAuth(PKCE)로 로그인해(`-antigravity-login`, 대시보드 Connect) Cloud Code Assist 프로젝트를 찾고(`loadCodeAssist`, 없으면 `onboardUser`), 기존 `* -> Antigravity` 변환기로 만든 요청 봉투에 프로젝트와 요청 정보를 채워 `v1internal:generateContent`·`streamGenerateContent`로 보냅니다. 요청의 `User-Agent`를 Antigravity 데스크톱 클라이언트와 같게 보내는데, 이는 첫 번째 파티 클라이언트로 위장하는 것이라 Google 약관에 어긋날 수 있습니다. 로그인에 쓰는 클라이언트 ID와 비밀값은 Antigravity 데스크톱 클라이언트에 들어 있는 공개 값입니다. 토큰 수 세기(`count_tokens`)와 `responses/compact`는 지원하지 않습니다. 생각 서명 재사용 캐시와 모델별 효과 변환은 이번에 옮기지 않았습니다. 실제 Google 서비스로는 검증하지 않았습니다. 스트림은 Gemini 실행기와 같이 중간 chunk의 사용량을 `cpaUsageMetadata`로 옮긴 뒤 변환기에 넘기고, 토큰 갱신 중 프로젝트가 비어 있으면 `loadCodeAssist`만 한 번 시도합니다(`onboardUser` 대기는 로그인에서만 합니다).
- GitHub Copilot과 Antigravity의 사용량 조회. Command Code처럼 서버에 새 코드를 두지 않고 대시보드의 사용량 버튼이 `/requests/api-call`로 조회합니다. Copilot은 비공식 `api.github.com/copilot_internal/user`에서 한도가 있는 항목(프리미엄 요청)의 남은 양과 초기화 날짜를 읽고, 이 주소에는 짧은 Copilot 토큰이 아니라 GitHub 로그인 토큰이 필요해서 `$TOKEN$` 치환이 Copilot 인증 정보에서는 `refresh_token`을 씁니다. Antigravity는 `v1internal:retrieveUserQuotaSummary`에 `project_id`를 보내 5시간·주간 한도를 읽으며, opencodex와 달리 403일 때 다른 `User-Agent`로 다시 시도하지 않습니다. 두 주소 모두 비공식이라 막히거나 바뀔 수 있고 실제 서비스로 검증하지 않았습니다. Nous Portal은 추론용 토큰으로 접근할 수 있는 잔액·사용량 주소가 공개돼 있지 않아 조회를 넣지 않았습니다. 대시보드는 성공한 조회 결과를 60초 동안 재사용해서 '전체 확인'을 반복해도 제공자를 다시 호출하지 않고, 개별 'Check quota' 버튼은 항상 새로 조회합니다.

- 모델별 사용량 집계와 새 조회 주소. `GET /v8/management/observability/usage/stats`(v0 표기 `GET /v0/management/usage-stats`)가 차원별 누적 토큰·캐시 합계를 돌려줍니다. `group_by` 쿼리로 차원을 고르며 값은 `model`(기본값), `provider`, `auth_index`입니다. 서버는 요청마다 발행되는 사용 기록을 메모리에서 세 차원(모델, 제공자, 계정)의 누적치로 접어 둡니다. Go 기준 커밋 `6fecc6e`에는 모델별 토큰 집계가 없습니다. Go는 인증 정보 단위의 성공·실패 횟수만 세고, 토큰 수치는 한 번 읽으면 사라지는 사용 대기열에만 있습니다. 집계는 기존 `observability.usage.usage-statistics-enabled` 플래그로 켜며 새 설정 키를 만들지 않습니다. 값은 메모리에만 있어 재시작하면 초기화됩니다. 기존 엔드포인트의 경로·응답 바이트·동작은 바뀌지 않습니다. 자세한 내용은 [사용량과 한도 조회](USAGE.md#per-model-rollup)를 보십시오.

## 의도한 차이

- 기본 `auth-dir`. 설정에 `auth-dir`가 없으면 horon-router는 `~/.horon-router`를 씁니다. Go의 기본값은 `~/.cli-proxy-api`입니다. 그래서 설정 없이 처음 실행하면 두 서버가 서로 다른 폴더의 계정 파일을 읽습니다. 설치 스크립트는 `~/.horon-router/auth`를 설정에 명시하므로 설치한 사용자는 영향을 받지 않습니다. 기존 Go 설정을 옮길 때는 `auth-dir` 값을 그대로 두거나 새 폴더로 옮깁니다. 로컬 폴더 선택이라 Go 호환에는 영향이 없습니다.
- Claude Code 신원. 같은 주 버전 안에서 측정 기준선(2.1.280) 이상인 진짜 Claude Code `User-Agent`는 Claude 계정으로 그대로 전달합니다. Go는 기준선이 속한 2.1 계열의 패치 릴리스만 전달합니다. 그래서 Claude Code 2.2 이상은 2.1.280으로 보내지고 제3자 클라이언트처럼 취급됩니다. 기준선보다 새로운 릴리스를 전달할 때는 잘 만들어진 `X-Stainless-Package-Version`과 `X-Stainless-Runtime-Version` 헤더를 함께 보내야 합니다. 이 헤더는 요청과 함께 업스트림으로 갑니다. 헤더가 없으면 전과 똑같이 2.1.280으로 위장합니다. Go는 두 헤더를 기준선 값으로 바꿉니다. 그래서 Go의 헤더가 전달한 `User-Agent`와 어긋날 수 있습니다. 그런 릴리스의 Haiku 도우미 요청(세션 제목, 사용 한도 확인)도 측정된 베타와 본문 모양이 유지되는 동안 같은 규칙을 따릅니다. Go는 기준선 튜플과 정확히 같을 때만 도우미를 확인합니다. horon-router가 전달한 새 릴리스에 과금 블록을 붙일 때, 그 블록의 `cc_version`은 그 릴리스의 버전입니다. Go는 기준선 버전을 씁니다. `stabilize-device-profile`을 켜면 Go의 2.1 패치 규칙이 그대로 적용됩니다. 안정화된 프로필은 정확히 기준선 튜플만 전달하기 때문입니다. 위의 Stainless 요구 사항, 도우미 규칙, 과금 버전은 안정화를 끈 경우에만 적용됩니다. 기준선 신원을 보내는데 거부된 `claude-cli` `User-Agent`는 인증 정보와 버전마다 최대 한 번만 로그에 남습니다(인증 정보마다 64칸이라 두 버전이 한 줄을 공유할 수 있습니다). 로그에는 인증 정보를 인증 인덱스로 표시합니다.
- thinking을 거부하는 Claude 모델에서 끄기. `reasoning_effort: "none"`, thinking 예산 0, 또는 `thinking: {"type": "disabled"}`를 Claude Opus 5.5, Sonnet 5.5, Fable 5와 5.1, Mythos로 보내면 effort `low`의 적응형 thinking이 됩니다. 이 모델들은 `disabled`에 400으로 답하고(Anthropic의 thinking 문제 해결 표), Go는 그대로 `disabled`를 보냅니다. 다른 Claude 모델은 여전히 `disabled`를 받습니다.
- Codex와 xAI WebSocket. 업스트림(요청을 실제로 받아 처리하는 제공자 서버)에 프레임 하나를 쓰는 시간은 10초로 제한합니다. 프레임 크기를 초당 128 KiB로 나눈 값(올림)이 더 길면 그 값을 씁니다. 제한을 넘긴 쓰기는 다른 쓰기 실패와 똑같이 처리됩니다. 업스트림이 이미 소켓을 1009(메시지가 너무 큼)로 닫았다면, 요청은 쓰기 실패와 같은 413을 받습니다. 그렇지 않으면 소켓을 버리고 새 소켓에서 요청을 한 번 재시도하거나, 이어지는 스트림에서는 재생 요청으로 답합니다. 조종(양방향) 스트림에서는 스트림이 시작된 뒤 쓰기가 실패하거나 시간이 초과되면 그 오류로 스트림을 끝냅니다. Go는 쓰기 마감 시간을 정하지 않습니다. 그래서 반쯤 열린 소켓이 300초 읽기 마감 시간까지 요청을 붙잡았습니다.
- 업스트림 연결. `api.anthropic.com`용 Claude 클라이언트는 모든 유휴 연결을 90초 동안 유지합니다. Go의 전송 계층은 호스트마다 유휴 연결을 최대 2개까지 시간 제한 없이 유지합니다(net/http 기본값). 그래서 동시 요청이 몰린 뒤 Go는 다시 연결하지만 horon-router는 그러지 않습니다.
- 업스트림 시간 초과. 고정 시간 제한이 있는 요청(Kimi와 xAI 로그인과 토큰(로그인 증명서 같은 값) 갱신, Codex와 Devin 모델 목록, 관리 API `api-call`)은 모든 리다이렉트 단계에 마감 시간 하나를 씁니다. Go의 `http.Client.Timeout`과 같습니다. 마지막 응답 본문 읽기는 따로 제한합니다. 그 요청을 보낼 때 남아 있던 시간을 씁니다. 그래서 느린 본문은 교환 시간을 제한 시간의 최대 두 배까지 늘릴 수 있습니다. Go의 마감 시간은 본문까지 포함합니다.
- 사용 한도 쿨다운(`routing.cooldown.max-trusted-cooldown`, 버그 수정, 기본 켜짐). 업스트림이 초기화 시간과 함께 429로 답할 때가 있습니다(Codex의 `resets_at`이 있는 `usage_limit_reached`, Claude의 `anthropic-ratelimit-unified-*-reset`, 또는 아무 제공자의 `Retry-After`). 이때 Go는 그 시간까지 계정을 쉬게 하고, 며칠 뒤여도 다시 묻지 않습니다. 제공자는 초기화를 앞당기는 일이 잦습니다. 그래서 Go는 안내된 시간이나 재시작 때까지 계정을 놀립니다. `save-cooldown-status`를 켜면 재시작해도 같은 대기를 되살립니다. horon-router는 처음에는 계정을 최대 1시간만 쉬게 하고, 그다음부터 다음 일반 요청 하나를 확인용으로 통과시킵니다(타이머나 백그라운드 요청은 없습니다). 업스트림으로 가는 것은 그 요청 하나뿐입니다. 그 요청이 답을 받을 때까지(또는 최대 30초 동안) 다른 요청은 그 계정을 쿨다운 중으로 봅니다. 재시도는 이런 대기 창을 기다리지 않습니다. 확인은 그 요청 자체의 응답이나 취소로만 끝납니다. 그 전에 골라 둔 요청(30초가 지난 앞선 확인 요청 포함)의 응답이나 취소는 계정을 풀지도, 다음 대기 창을 열지도 않습니다. 스트리밍 응답은 첫 이벤트가 도착하는 순간부터 인정합니다. 그래서 스트림이 도는 동안 다른 요청이 그 계정을 씁니다. 예외가 하나 있습니다. 묶인 `openai-compatibility` 모델 별칭(한 별칭 아래 여러 모델)에서 어떤 모델이 계정이 아니라 자기 대기 창을 가질 때가 있습니다. 그 창이 끝난 뒤 함께 도착한 별칭 요청들은 그 모델을 각각 확인할 수 있습니다. 예약은 고를 때 별칭 기준으로 잡히고, 모델 선택은 나중에 묶음이 하기 때문입니다. 또 다른 429로 끝난 창은 다음 창을 두 배로 만듭니다. 성공하면 이 증가가 멈춥니다. 대기 시간은 안내된 초기화 시간을 넘지 않습니다. 다만 Go가 더하는 것들은 예외입니다. 10초 최소값과, Claude의 초기화 시간에 더하는 1~30초의 무작위 지연입니다. 대기 창이 열리기 전에 골라 둔 요청의 성공(429를 넘겨 살아남은 스트림)은 창을 자기 확인 요청에 맡깁니다. Go는 어떤 성공이든 쿨다운을 지웁니다. 창 안에서 동시에 온 429는 창을 유지하거나, 더 이른 초기화 시간을 말하면 창을 줄입니다. 계정의 확인 요청은 계정의 창에 답하는 것이지 모델의 창에 답하는 것이 아닙니다. 그 모델은 자기 확인 시간을 유지하고 자기 확인 요청을 따로 받습니다. 계정의 제한된 창 아래에서도, 원인이 무엇이든 모델 자체의 쿨다운은 그 모델 기록에 자기 마감 시간을 유지합니다. 계정 기록은 계정 확인 요청 전까지 그 모델을 붙잡습니다. 그래서 계정이 더 일찍 초기화돼도 모델이 더 빨리 돌아오지 않습니다. Go는 두 마감 시간 중 더 늦은 쪽을 모델 기록에 씁니다. 창이 두 배가 된 횟수는 Go의 `backoff_level`(뜻은 그대로 유지됩니다)과 별개이고, horon-router가 `.cds` 파일에 쓰는 모든 사용 한도 기록에 `quota.trust_windows` 필드로 따로 저장합니다(Go는 무시합니다). 기록은 쿨다운이 도는 동안에만 저장합니다. 그래서 창이 끝난 뒤 재시작하면 다시 1시간부터 시작합니다. horon-router가 쓴 기록은 저장된 그대로 복원됩니다. Go가 썼거나 이 변경 전에 쓴 `.cds` 기록은 첫 번째 제한을 받습니다. 모델의 횟수는 인증 정보 전체에 걸친 창 때문에 낮아지지 않습니다. 안내된 초기화 시간은 남습니다. `.cds` 기록과 오류 이벤트는 그것을 `quota.next_recover_at`(Go의 뜻)으로, 확인 시간을 `next_retry_after`로 보고합니다. 관리 API의 쿨다운 항목에는 `recover_at`이 추가됩니다. 그래서 대시보드에 "Limited until X · next check in Y"가 표시됩니다. 이런 항목은 창이 끝나고 안내된 초기화 시간이 아직 남아 있으면 `remaining_seconds` 0으로 목록에 남습니다. 드는 비용은 이렇습니다. 429마다 비교 한 번, 기록된 결과마다 두 키로 하는 확인 검사(고를 때마다, 스트림이 시작할 때마다), 스트림이 시작되거나 성공이 계정 창을 끝낼 때 쿨다운 항목 스캔 한 번, 쿨다운 항목마다와 요청마다 창 세대용 4바이트, 그리고 인증 정보와 모델마다 창당 실제 업스트림 요청 하나입니다. `max-trusted-cooldown: 0`은 Go의 동작을 되돌립니다. 설정을 다시 읽어 이 값이 바뀌면 다시 읽은 뒤 고른 요청부터 적용됩니다. 제한된 창은 자기 제한을 유지하고 자기 확인 요청으로 끝납니다. 다만 그런 요청에서 온 429가 창 안에서 더 늦은 초기화 시간과 함께 도착하면, Go에서처럼 그 시간이 제한을 대체합니다. Go는 이 키가 `config.yaml`에 있어도 시작할 때 무시합니다. Go의 관리 API가 파일을 다시 쓰면 이 키를 주석으로 옮깁니다. Go가 모르는 키는 모두 그렇게 합니다.
- 시작. 클라우드 배포 모드가 아닐 때 설정을 읽지 못하면 horon-router는 0이 아닌 상태로 종료합니다. 그래서 서비스 관리자가 실패를 알아챕니다. Go는 0으로 종료합니다.
- 검색(discovery). 서브타입 PTR 질의에 답합니다(Go의 zeroconf 라이브러리는 이런 질의를 전혀 처리하지 못합니다). 답은 선택한 모든 네트워크 인터페이스로 나갑니다.
- `.env`. 따옴표로 묶인 값 안의 UTF-8이 아닌 바이트는 손실을 감수하고 디코딩합니다. Go는 원래 바이트를 그대로 둡니다.
- 관리 API에서 시작한 OAuth(비밀번호 없이 로그인하는 방식) 로그인. 대기 중인 콜백은 `auth-dir`에 `.oauth-<provider>-<state>.oauth` 파일로 쓰지 않고, 로그인 세션과 함께 메모리에 보관합니다.
- Claude. `platform_url`은 로그인 결과 페이지에서 HTML 이스케이프합니다. 인증 파일은 모드 0600으로 원자적으로 씁니다. SSH 포트 포워딩 안내는 나가는 인터페이스의 IP 주소를 보여 줍니다.
- 플러그인. Windows에서 플러그인 로드를 지원하지 않습니다. cgo 없이 빌드한 Go와 같습니다.
- 플러그인, Go가 제한 없이 읽는 곳의 크기 제한. 플러그인 프런트엔드 인증 제공자는 요청 본문을 최대 64 MiB까지 읽습니다. 경로와 같은 제한입니다. 그보다 크면 키를 보내지 않았더라도 `413`과 `{"error":"request body too large"}`로 거부합니다. 플러그인 저장소 응답(레지스트리, 릴리스 메타데이터, 릴리스 자산, 직접 받는 산출물)은 256 MiB에서 멈춥니다. 선언된 산출물 크기는 이 값을 낮출 수만 있습니다. 플러그인 압축 파일 안의 라이브러리는 최대 256 MiB까지 풀릴 수 있습니다. `host.http.do`는 응답을 최대 64 MiB까지 버퍼링하고 그 뒤에는 읽기 오류로 실패합니다. `host.http.do_stream`은 제한이 없습니다. 사용 한도 확인의 답은 `requests/api-call`처럼 최대 64 MiB까지 읽습니다.
- 플러그인 저장소. GitHub의 `X-Ratelimit-Reset`이 9999년 말보다 뒤면 그 시각으로 취급합니다. 그래야 쿨다운 시간을 표시할 수 있습니다. Go는 어떤 값이든 그대로 둡니다.
- 검색 모드. 플러그인이 로드되기 전에는, horon-router가 정의하지 않은 플래그(플러그인이 추가하는 불리언 플래그일 수 있습니다)가 뒤따르는 `-discover`나 `-discover-json`을 자기 값으로 가져가지 않습니다. 그래서 `-some-plugin-flag -discover`는 플러그인과 `.env`를 로드하지 않고 검색을 실행합니다. Go는 모르는 플래그마다 값을 받는 것으로 취급합니다. 그리고 전체 파싱이 검색을 고르기 전에 플러그인과 `.env`를 로드합니다. horon-router가 정의한 플래그는 Go와 똑같이 동작합니다.
- 플러그인, `.env`. 명령줄 플래그를 추가하는 플러그인이 로드되기 전에 이 파일을 읽습니다. 그래서 플러그인이 그 변수를 봅니다. Go는 플래그 파싱 뒤에 읽습니다.
- 플러그인 로그인. 로그인이 인증 파일 여러 개를 돌려주는데 뒤의 하나를 저장하지 못하면, 앞의 것들을 데이터 손실 없이 되돌립니다. 로그인이 만든 파일은 로컬에서도, 설정된 저장소에서도 지웁니다. 전에 있던 파일은 이전 내용을 되찾고, 저장소 사본은 그 파일에서 동기화합니다. Go는 두 종류 모두 저장소 사본과 함께 지웁니다.
- 플러그인, 프런트엔드 인증. 플러그인이 수락된 요청과 함께 돌려주는 메타데이터는 보관하지 않습니다. Go에서는 Home 모드만 이 값을 읽습니다.
- 플러그인, 모델 라우터. 라우터에 보내는 사용 가능한 제공자 목록은 `kimi.com`이나 `kimi.ai`로 입력된 Kimi 인증 정보를 그 키 그대로 표시합니다. 여기서 인증 정보 선택은 키를 적힌 그대로 맞추기 때문입니다. Go는 이들을 `kimi`와 `kimi-ai`로 표시하고, 고를 때 두 표기를 합칩니다.
- 플러그인, `host.http.*`. Go의 파서와 WHATWG 파서가 호스트를 다르게 읽는 URL은 보내지 않고 거부합니다.
- 로그. Go가 정의하지 않은 구조화 필드는 Go가 아는 필드 뒤에 출력합니다.
- 프로세스 로그. 직접 켜야 하는 `--log-file PATH` 플래그는 기존의 10 MiB 회전 로거로 표준 출력을 대체합니다. `logs-max-total-size-mb`가 양수면 이 로거의 회전 파일들이 일반 로그 디렉터리와 그 예산을 나눠 씁니다. PATH가 다른 곳에 있어도 마찬가지입니다. 기존 정리기가 분 단위 일정에 따라 가장 오래된 로그를 지웁니다. 기본값인 `0`이면 일반 로그는 제한이 없습니다. 대신 PATH의 시각별 회전 파일에 별도의 총 32 MiB 상한이 붙고, 시작할 때와 설정을 다시 적용할 때, 회전할 때 적용합니다. 별도 타이머는 없습니다. 두 정리 경로 모두 쓰기 위해 열어 둔 파일은 지우지 않습니다. 그 활성 파일은 예산을 넘을 수 있습니다. 일반 로그 디렉터리 밖에서는 PATH와 그 시각별 회전 파일만 셉니다. `logging-to-file: true`는 여전히 `main.log`, 대시보드 로그 보기, 기존 크기 정리기를 씁니다. 끄면 `--log-file`로 돌아갑니다. 콘솔을 떼어내는 것은 서비스 직전의 일반 Windows 서버뿐입니다. 로그인, 가져오기, 검색, TUI, 플러그인 명령은 콘솔을 유지합니다. 켜져 있으면 출력 파일 하나를 열어 둡니다. 기존 로그 쓰기 외에 스레드나 타이머를 더 만들지 않고, 추론 요청에도 부담을 주지 않습니다. Go에는 이런 플래그가 없습니다.
- 작업 디렉터리. 직접 켜야 하는 `--working-dir DIR` 플래그는 `.env`, 플러그인 부트스트랩, 설정, 상대 경로를 읽기 전에 디렉터리를 바꿉니다. Windows 설치 프로그램은 로그인할 때와 설치 후 모두 이 플래그를 넘깁니다. 비용은 시작할 때만 들고, Go의 플러그인 명령줄 값에는 넘기지 않습니다. Go에는 이런 플래그가 없습니다.
- 릴리스 확인. 대시보드는 클릭할 때만 확인합니다. `GET /server/latest-version`은 이전에 비어 있던 릴리스 URL을 채웁니다. 공개된 horon-router 최신 릴리스 리다이렉트로 익명 HEAD 요청 하나를 보내고, 리다이렉트를 따라가지 않습니다. 성공한 태그는 12시간 동안 캐시합니다(타임스탬프와 태그 하나, 만료 타이머 없음). `HORONROUTER_NO_UPDATE_CHECK=1`은 시작할 때 확인을 끕니다. 릴리스 확인은 설정된 `proxy-url`을 쓰고, 없으면 환경 프록시를 씁니다. 토큰이나 쿠키는 절대 보내지 않습니다. 프록시 인증 정보는 사용자의 프록시로만 갑니다. TLS 검증은 켜고 리다이렉트는 끕니다. Go는 호출할 때마다 GitHub API에 묻고 환경 토큰을 붙일 수 있습니다. 그 토큰을 빼는 것이 인증 정보 유출 수정입니다. 추론 요청에는 부담이 늘지 않습니다.
- 설정 쓰기. 관리 API가 설정 하나를 바꿀 때 `config.yaml`의 나머지는 바이트 그대로 남습니다. Go는 파일을 다시 인코딩합니다. 그래서 `yes`, `on` 같은 YAML 1.1 불리언이 `true`로 바뀝니다.
- 감시자. 설정 변경이 `auth-dir`를 옮기면 horon-router는 새 디렉터리를 감시하기 시작합니다. Go는 재시작할 때까지 옛 디렉터리를 계속 감시합니다.
- 감시자, 파일 변경 알림을 설정할 수 없을 때(Linux의 inotify 인스턴스나 감시 개수 한도, macOS의 파일 디스크립터 한도, 또는 Linux, macOS, Windows가 아닌 운영체제). horon-router는 경고를 한 번 남기고, 대신 설정 파일과 인증 파일을 2초마다 확인합니다. Go는 시작할 때 멈춥니다. inotify나 kqueue 인스턴스를 만들 수 없거나(운영체제에 fsnotify 백엔드가 없을 때) `horonrouter: failed to create watcher`로 멈추고, 설정 파일이나 인증 디렉터리를 추가할 수 없으면 `horonrouter: failed to start watcher`로 멈춥니다. FreeBSD, OpenBSD, NetBSD, DragonFly, illumos/Solaris에서는 Go가 kqueue나 FEN 이벤트로 다시 읽는 반면, horon-router는 2초마다 폴링합니다. Go와 마찬가지로 네트워크나 FUSE 파일 시스템에서 다른 기기가 만든 변경은 다음 로컬 변경이 있을 때까지 보고되지 않을 수 있습니다. NFS, 9p(WSL2의 /mnt/c 같은 것), sshfs에서는 보고되지 않습니다. SMB/CIFS 공유에서는 서버에 따라 보고되지 않을 수 있습니다(Windows에서는 ReadDirectoryChangesW가 서버에 변경 알림을 요청하고, SMB 3.0 서버는 이를 보낼 수 있습니다).
- 감시자, 심볼릭 링크. horon-router는 설정 파일로 가는 길에 있는 심볼릭 링크를 담은 폴더, 인증 폴더, 심볼릭 링크된 인증 파일도 감시합니다. 그래서 Kubernetes Secret 갱신(`..data` 교체)이나 새 릴리스 폴더로 가는 `ln -sfn`이 다시 읽힙니다. Go의 fsnotify는 설정 파일과 인증 폴더만 감시해서 이런 변경을 놓칩니다.
- 토큰 갱신. 갱신 루프는 다음 토큰이 만료될 때까지 잠들고, 어떤 인증 정보든 만료될 수 있으면 깨어 있는 시간 기준 최소 10분마다 다시 확인합니다. Go는 30초마다 확인합니다. 컴퓨터가 잠에서 깨거나 시계가 앞으로 건너뛴 뒤에는, 그 사이 만료된 토큰을 401을 받은 첫 요청이 갱신합니다(왕복 한 번 추가, 다른 인증 정보는 약 1초 뒤에 갱신됩니다). 아니면 10분 안에 갱신합니다.
- 모델 목록. Home 모드 밖에서는 Codex 클라이언트 목록을 처음 내려받는 시점이 세 가지입니다. Codex 인증 정보가 있을 때, Codex 클라이언트가 `/v1/models?client_version=...`를 요청할 때, 또는 Codex 클라이언트가 `client.codex.optimize-multi-agent-v2`를 켠 Responses 요청을 보낼 때입니다. Devin 목록은 Devin 인증 정보가 있을 때 내려받습니다. Go는 쓰든 안 쓰든 시작할 때와 3시간마다 둘 다 내려받습니다. Home 모드에서 horon-router는 Go처럼 실행할 때 둘 다 시작합니다. 첫 내려받기가 끝나기 전까지는 Codex 클라이언트 목록 응답과 `spawn_agent` 모델 목록이 바이너리에 내장된 목록을 씁니다. 끝난 뒤에는 Go와 일치합니다. 목록을 갱신할 때마다 마지막으로 설치한 목록의 `ETag`를 `If-None-Match`로 보냅니다. 그래서 바뀌지 않은 목록은 `304`로 끝납니다. Go는 매번 파일 전체를 내려받습니다.
- 감시자 시작. horon-router는 감시자가 시작할 때 `config.yaml`을 한 번 읽습니다. 그래서 설정을 읽은 뒤 감시가 시작되기 전에 이뤄진 수정이 반영됩니다. Go는 파일을 다시 읽지 않고 감시를 시작합니다. 그래서 다음 수정이 있을 때까지 옛 설정을 유지합니다.
- 관리 패널. horon-router는 대시보드를 내려받거나 갱신하지 않습니다. 바이너리에 내장돼 있습니다. Go는 패널을 처음 요청할 때 `management.panel-github-repository`에서 내려받고, `management.disable-auto-update-panel`이 설정되지 않았으면 3시간마다 새 패널을 확인합니다. horon-router는 두 설정을 모두 받아들이고 타입을 확인해 `config.yaml`에 보관합니다(관리 API로 `panel-github-repository`를 null로 설정하면 Go처럼 Go의 기본 저장소를 기록합니다). 하지만 어디서도 이 값을 읽지 않습니다. `management.disable-control-panel`은 여전히 내장 대시보드를 끕니다.
- 로그인 오류. 관리 API에서 시작한 Codex, Kimi, Meta, xAI, Devin 로그인이 실패하면, 세션 오류는 Go의 메시지, 상태, OAuth 오류 코드를 유지합니다. 다만 업스트림 응답 본문, OAuth 오류 설명, 디코더 세부 정보는 빼놓습니다. Go는 이런 것들을 함께 넣는데, 여기에 토큰이 들어 있을 수 있습니다. 게다가 콜백 경로는 관리 키 없이 세션 상태를 가진 사람 누구에게나 세션 오류를 보여 줍니다. 예를 들어 실패한 Codex 코드 교환은 "token exchange failed with status 400"에서 끝나는데, Go는 거기에 응답 본문을 덧붙입니다.
- 로그에서 가린 키. Go는 요청 로그와 쿼리 문자열에 있는 API 키, 토큰, 시크릿을 양끝 몇 바이트만 남겨 가립니다. 다만 1~2바이트짜리 값은 그대로 둡니다. horon-router는 이런 값에 `...`를 씁니다. 그래서 짧은 클라이언트 키가 로그에 나타나지 않습니다.
- 관리 API의 AI Studio 릴레이 인증 정보. `/v1/ws`에 연결된 브라우저는 실행 중에만 있는 인증 정보로 표시됩니다. `created_at`은 관리 API가 그 인증 정보를 처음 표시한 시각입니다. `updated_at`과 `modtime`은 그 인증 정보의 현재 버전을 처음 표시한 시각입니다. 그래서 상태나 필드를 고치면 이 값이 움직이고 요청은 움직이지 않습니다. Go는 브라우저가 연결할 때 둘 다 설정하고, 요청 결과마다 `updated_at`을 옮깁니다. horon-router의 인증 정보 저장소는 타임스탬프를 보관하지 않습니다.
- `DELETE /v8/management/credentials`(또는 v0의 `auth-files`)로 AI Studio 릴레이 인증 정보를 지우면 404 "auth file not found"로 답하고 디스크의 무엇도 건드리지 않습니다. 이 인증 정보에는 파일이 없습니다. 그래서 Go는 `auth-dir/<ID>`로 대신 찾습니다. 그 이름의 파일이 있으면 Go는 그 파일을 지우고 인증 정보도 지웁니다.
- 요청 로그의 쿠키. Go는 `Cookie`와 `Set-Cookie` 값을 요청 로그와 강제 오류 로그에 그대로 씁니다. horon-router는 이름에 `cookie`가 들어간 헤더의 값 전체를 `<redacted>`로 씁니다. 클라이언트 구역과 업스트림 구역 모두 그렇습니다. 세션 쿠키가 인증 정보이기 때문입니다. 업스트림으로 가고 클라이언트로 돌아오는 헤더는 그대로입니다.
- 요청 로그의 업스트림 URL. Go는 기록한 요청마다 업스트림 URL을 그대로 씁니다. 그래서 설정된 `base-url`에 있는 인증 정보가 로그에 들어갑니다. horon-router는 `user:password@` 부분을 `<redacted>`로 바꿉니다. 또 민감한 쿼리 값(`key`, 그리고 이름에 `api-key`, `apikey`, `api_key`, `token`, `secret`이 들어간 것)을 클라이언트 URL을 가릴 때와 같은 방식으로 가립니다. 요청은 설정된 URL로 그대로 갑니다.
- 취소된 xAI 요청의 사용 기록. xAI HTTP 요청이 진행 중일 때 클라이언트가 사라지면, 실패 기록은 Go처럼 상태 499와 함께 `context canceled`를 씁니다. 다만 취소가 전송 단계에 걸렸을 때 Go의 문구가 붙이는 메서드와 URL(`Post "<url>": context canceled`)은 빼놓습니다. 설정된 기본 URL은 쿼리에 인증 정보를 담을 수 있습니다.
- xAI 요청 로그. xAI 비디오 상태 확인의 API REQUEST 구역은 업스트림으로 보낸 메서드인 `HTTP Method: GET`을 씁니다. Go는 그 `GET`을 포함해 모든 xAI 요청을 `POST`로 기록합니다.
- 비디오 결과 계정 연결 캐시의 크기 상한. xAI 비디오 결과를 만든 자격 증명에 묶는 프로세스 전역 캐시(`crates/horon-server/src/videos.rs`)에 상한을 둡니다. 항목 65,536개와 총 64 MiB입니다. 넘으면 만료된 항목을 먼저 지우고, 만료가 하나도 없을 때만 가장 먼저 만든 항목부터 지웁니다. 보관 시간(`multimedia.video-result-auth-cache-ttl`)과 제거된 키의 `None` 폴백은 그대로입니다. Go에는 이 캐시에 크기 상한이 없습니다. 상한은 정상 운전(TTL 3시간 × 현실적 생성률)에서 도달하지 않는 방어선이라 평상시 동작은 Go와 같습니다.
- Antigravity 서명 캐시의 크기 상한. Claude -> Antigravity 변환기가 클라이언트가 서명 없이 되돌려보낸 사고 텍스트의 서명을 복원하는 데 쓰는 프로세스 전역 캐시(`crates/horon-translate/src/replay_cache.rs`)에 상한을 둡니다. 전체 131,072항목과 모델 그룹당 8,192항목입니다. 넘으면 만료된 항목(서명 보관 시간 3시간)을 먼저 지우고, 만료가 하나도 없을 때만 가장 오래전에 쓴 항목부터 지웁니다. 상한에 밀려 지운 항목은 복원하지 못해 그 턴은 캐시가 없을 때와 똑같이 처리됩니다. Go에는 이 서명 캐시에 크기 상한이 없습니다. 상한은 정상 운전(3시간 보관 × 현실적 쓰기율)에서 도달하지 않는 방어선이라 평상시 복원 결과는 Go와 같습니다.
- OAuth 콜백. 인증이 필요 없는 `POST /v8/management/oauth/callback`(그리고 v0의 `oauth-callback`)은 본문을 최대 64 KiB까지 받습니다. Go는 제한 없이 읽습니다. 실제 콜백은 수백 바이트입니다. 이 제한은 인터넷에서 접근할 수 있는 서버를 보호합니다.
- Responses WebSocket. 인증 정보에 고정된 이어지는 스트림이 401이나 429로 실패하면 클라이언트를 항상 1012(HTTP로 재생)로 닫습니다. Go에서는 같은 오류가 업스트림 소켓도 닫습니다. 또 연결 끊김 감시자가 1012 대신 그 오류로 클라이언트를 먼저 닫을 수 있습니다.
- 세션 고정. 세션 ID가 없는 요청의 본문이 배열과 객체를 128단계 넘게 중첩하면, 그 메시지로 이전 대화와 맞추지 않습니다. 대신 지시문과 첫 사용자 메시지에서 뽑은 세션 신원을 유지합니다. 클라이언트 키가 없는 요청과 같습니다. Go는 늘어나는 스택에서 깊이에 상관없이 맞춥니다. 반면 네이티브 스택에서 같은 순회를 하면 넘쳐서 서버가 멈춥니다. 실제 대화는 훨씬 얕게 중첩합니다.
- 세션 고정. 라우팅 변경(방식이나 `session-affinity` 설정)이 대화 매처를 갈아 끼울 때, 접근 카운터는 계속 셉니다. Go에서는 새 매처가 0부터 다시 시작합니다. 그래서 변경 전에 고른 요청이 그 뒤에 실패하면, 변경 후에 묶인 대화를 지울 수 있습니다. 그러면 다음 요청이 다시 묶을 때까지 그 계정을 잃습니다.
- 세션 고정, 바이트 한도. horon-router의 세션 대화 접두사 매처는 Go와 달리 항목 수 한도(그룹 4,096개, 접두사 항목 262,144개, 대화당 최대 1,024턴)에 더해 바이트 한도를 둡니다. 그룹 전체 합계 128 MiB, 그룹 하나당 4 MiB가 기본값입니다. 한도에 닿으면 항목 수 한도와 마찬가지로 가장 오래된 그룹부터 지웁니다. 측정된 사용량은 이 값보다 훨씬 낮아 실제로는 닿지 않는 안전장치입니다. Go의 매처는 항목 수만 제한하고 바이트 수에는 한도가 없습니다(`crates/horon-server/src/lcp.rs`).
- 요청 로그. 기록된 본문의 Brotli 인코딩이 잘못됐을 때, horon-router는 Go가 로그에 쓰는 부분 디코딩 바이트를 빼놓을 수 있습니다. 또 디코더의 오류 문구가 Go와 다릅니다. 올바른 압축 본문은 Go와 똑같이 기록합니다.
- Kimi, Meta, Devin 요청 로그. 응답이 오기 전에 업스트림 요청이 실패하면, API RESPONSE 구역의 `Error:` 줄에 `upstream request failed` 같은 horon-router 자체 메시지가 들어갑니다. Go는 이 자리에 자기 HTTP 클라이언트의 오류(`Post "<url>": ...`)를 씁니다. Kimi나 Meta의 오류 응답은 horon-router가 읽는 부분인 처음 16 MiB까지 기록합니다. Go는 본문 전체를 기록합니다. Kimi나 Meta 스트림이 읽기 오류로 끝나면서 apply_patch 종료 검사도 실패하면, 로그는 읽기 오류를 남깁니다. Go는 그런 경우 이 오류를 빼놓습니다.
- Devin 요청 로그. 스트림 끝 요약(thinking, content, signature)은 스트림이 시작할 때 `request-log`가 켜져 있을 때만 수집합니다. 그래서 아무도 기록하지 않는 스트림은 메모리에 남지 않습니다. `request-log`를 켤 때 이미 돌고 있던 스트림은 요약을 받지 않습니다. Go는 스트림마다 요약을 하나씩 모읍니다.
- Codex 실시간 요청 로그. `POST /v1/live`, `POST /v1/realtime`, `POST /v1/realtime/calls`의 로그에서 SDP 본문의 ICE 인증 정보(`a=ice-ufrag:`과 `a=ice-pwd:` 값, JSON이나 multipart 본문 안에 있는 것도 포함)를 `[REDACTED]`로 씁니다. 다운스트림 구역과 업스트림 구역 모두 그렇습니다. Go는 그런 본문을 그대로 기록합니다. 클라이언트와 업스트림으로 보내는 바이트는 바뀌지 않습니다.
- `PUT /v0/management/config.yaml`. 올린 내용을 검사하기 전에 주석 줄의 들여쓰기를 뺍니다. 그래야 검사가 실제로 쓰이는 바이트를 봅니다. Go는 올린 그대로 검사하고 쓰면서 들여쓰기를 뺍니다. `#` 줄이 블록 스칼라 안에 있으면, Go는 다시 읽히지 않는 YAML로 `config.yaml`을 덮어쓰고 `500 reload_failed`로 답할 수 있습니다. horon-router는 `400 invalid_yaml`로 답하고 파일을 건드리지 않습니다. 두 응답이 Go와 다릅니다. `port: abc` 같은 타입 불일치는 `422 invalid_config`입니다(Go는 `400 invalid_yaml`). 또 YAML 문법 메시지가 다른 파서에서 오므로 상태와 오류 코드만 일치합니다.
- 터미널 UI(`-tui`)
  - 답장은 그것을 요청한 탭으로 갑니다. Go는 활성 탭에만 답장을 넘깁니다. 그래서 탭을 바꾼 뒤 도착한 답장은 사라집니다(진행 중이던 OAuth 폴링은 끝나지 않습니다).
  - 텍스트 입력 칸에 포커스가 있으면 Ctrl+C를 뺀 모든 키가 그 칸으로 갑니다. Go는 입력 중에도 `q`로 종료하고, `L`로 언어를 바꾸고, Tab으로 탭을 바꿉니다. 비밀번호 화면에서는 입력 칸이 비어 있는 동안 `q`와 `L`이 원래 뜻을 유지합니다.
  - 상태 표시줄은 터미널 마지막 줄에 있습니다. Go는 그 아래에 빈 줄 두 개를 남깁니다.
  - 긴 줄은 터미널 가장자리에서 잘립니다. 가로 스크롤(`h`/`l`)이 없습니다. 커서는 깜빡이지 않고, Ctrl+V는 시스템 클립보드를 읽지 않습니다(터미널 붙여넣기는 됩니다).
  - 클라이언트 API 키를 추가할 때 `{"old": key, "new": key}`를 보냅니다. 키가 없으면 이 방식이 키를 추가합니다. Go는 `{"old": null, "new": key}`를 보내는데, Go 자신의 서버가 이를 `400 missing fields`로 거부합니다.
  - 인증 파일 탭이나 API 키 탭에서 시작한 삭제나 편집은 선택했던 항목에 적용됩니다. Go는 확인할 때 목록 위치를 다시 찾습니다. 그래서 그 사이 새로 고침이 일어나면 다른 파일을 지우거나 다른 키를 바꿀 수 있습니다. API 키는 위치로 지정하므로, 새로 고침이 선택한 키를 옮기면 작업을 취소합니다.
  - horon-router 서버에서는 OAuth 탭이 Antigravity를 지원하지 않는 것으로 표시하고 시작하지 않습니다. Go 서버는 여전히 이 기능을 제공합니다.
  - `-tui -management-base-url URL`은 순수 클라이언트입니다. 로컬 설정이나 저장소, Home 부트스트랩 없이 시작합니다. Go는 이런 것들을 먼저 로드합니다. 그래서 로컬 설정이 없으면 실패하고, 클라우드 모드에서는 기다립니다.
  - `-tui -standalone`은 설정에 관리 키가 없거나 `MANAGEMENT_PASSWORD`가 없어도 동작합니다. 생성된 비밀번호(또는 `-password`로 준 비밀번호)를 루프백에서 받아들입니다. 설정을 다시 읽은 뒤에도 그렇습니다. Go는 관리 키가 설정되지 않으면 모든 관리 요청을 거부합니다. 그래서 Go의 단독 TUI는 이때 연결하지 못합니다. TUI는 서버가 실제로 바인딩한 주소로 연결합니다. 그래서 `port: 0`과 IPv6 루프백이 동작합니다. `server.tls` 설정이나, 루프백도 와일드카드 주소도 아닌 호스트는 오류와 함께 거부합니다. Go에서는 이런 경우 연결 시도 30번 뒤에 실패합니다.
- `pprof`(계획 중, 아직 horon-router에 없음). 리스너는 index, `cmdline`, `symbol`을 제공할 예정입니다. 또 선택 기능을 켠 빌드에서는 CPU `profile`을 제공합니다. Go 런타임의 프로파일(`heap`, `allocs`, `goroutine`, `block`, `mutex`, `threadcreate`, `trace`)은 Rust에 대응하는 것이 없어서 `501`과 함께 간단한 메시지로 답할 예정입니다. 기능을 켜지 않으면 `profile`도 `501`로 답하고 그 기능 이름을 밝힙니다.
- Codex 실시간 호출용 WebRTC 미디어 릴레이(`oauth.providers.codex.live-media-relay`). 모든 Go 빌드에 들어 있고, 설정으로 켭니다. horon-router에서는 선택 빌드 기능입니다(`cargo build --release -p horon-router --features horon-server/media-relay`). 릴리스 실행 파일과 Docker 이미지는 이 기능 없이 빌드됩니다. 그래서 호출은 업스트림과 미디어를 직접 협상합니다. 릴레이를 켠 빌드에서는 TCP나 TLS로 접근하는 TURN 서버를 경고와 함께 건너뜁니다. WebRTC 라이브러리가 그런 서버로는 후보를 모으지 못하기 때문입니다. UDP를 쓰는 TURN과 STUN은 동작합니다. 업스트림 피어의 후보 수집은 6초 뒤에 멈추고, 그때까지 모은 후보로 통화를 이어 갑니다. STUN 서버가 침묵하면 라이브러리가 수집을 끝내지 않기 때문입니다. Go는 수집이 끝나거나 요청이 취소될 때까지 기다립니다. 그래서 릴레이 주소를 할당하는 데 6초 넘게 걸리는 TURN 서버는 Go에서는 릴레이 후보를 내놓지만 horon-router에서는 그러지 않습니다.
