# 여러 구독을 묶는 게이트웨이 설계 조사

조사일은 2026-10-10입니다. 실행 코드는 변경하지 않았습니다.

## 결론

현재 Rust 프록시를 유지하면서 **대화별 계정 고정 + 사용량 영역별 소진 판단 + 명시적인 제공자·모델 대체 목록**을 추가하는 것이 맞습니다. 요청마다 남은 양이 가장 많은 계정으로 옮기는 방식은 긴 코딩 대화의 캐시와 응답 일관성을 해칩니다.

새 대화를 배정할 때는 사용량과 초기화 시각을 보고, 진행 중인 대화는 현재 계정에 남깁니다. 계정이 소진되면 같은 모델을 제공하는 다른 독립 사용량 영역을 먼저 찾고, 그것도 없으면 미리 허용한 다른 모델로 옮깁니다. 전환 이후에는 새 계정을 유지하고 이전 계정이 복구됐다는 이유만으로 돌아가지 않습니다.

여기서 “자연스러운 전환”은 모든 내부 상태를 옮긴다는 뜻이 아닙니다. 이식 가능한 대화 내용을 보존하면서 다음 실행을 이어가는 것입니다. 제공자의 내부 캐시는 다른 제공자로 복사할 수 없으며 모델 변경은 답변 성향도 바꿉니다.

### LiteLLM

[공식 라우팅 문서](https://docs.litellm.ai/docs/routing)는 순환·가중·사용량·지연·최소 실행 수 기반 선택과 세션 고정, 대기 상태, 대체 모델을 분리합니다. Redis를 쓰면 여러 인스턴스가 세션 고정과 사용량 상태를 공유합니다.

조사 시점 문서는 고정 대상이 대기 상태면 다른 대상을 쓰되 원래 고정을 보존해 복구 후 돌아가는 동작도 설명합니다. 긴 코딩 대화에는 이를 그대로 적용하기보다 **한 번 전환하면 새 대상에 재고정**하는 정책을 권합니다. 돌아갈 때마다 다시 캐시를 만들거나 상태 이전 문제가 생길 수 있기 때문입니다.

개인용 단일 Rust 프로세스에는 Redis를 먼저 추가하지 않습니다. 여러 인스턴스를 운영하는 시점에 공유 예약·사용량·세션 상태를 도입하면 됩니다.

## 3. 선택 가능한 방식

| 번호와 방식 | 장점 | 단점 | 권장 용도 |
|---|---|---|---|
| 1. 우선순위 소진 후 전환 | 예측하기 쉽고 한 대화의 캐시를 보존하기 좋음 | 특정 구독을 먼저 소모함 | 첫 버전 기본값 |
| 2. 대화 고정 + 초기화 임박 우선 | 곧 사라질 구독 할당량을 먼저 활용 | 초기화 자료가 없으면 판단이 약함 | 새 대화 배정의 기본 후보 |
| 3. 대화 고정 + 남은 용량·실행 수 균형 | 여러 병렬 작업에 배정하기 좋음 | 사용량 자료가 늦으면 동시 과배정 가능 | 병렬 에이전트가 많은 경우 |
| 4. 작업 유형별 모델 선택 | 짧은 작업과 깊은 추론을 나눔 | 품질 평가와 추가 선택 비용이 필요 | 기본 전환이 안정된 후 |
| 5. 요청마다 순환·최저 지연 | 짧은 독립 요청을 분산하기 좋음 | 긴 대화의 캐시와 모델 일관성 손실 | 독립 분류·배치 작업 |

권장 조합은 1번의 명시적 대체 순서에 2번을 새 대화 배정 정책으로 붙이는 것입니다. 사용량 여유가 충분한 후보 사이에서 초기화 임박 계정을 고르고 진행 중인 대화는 그대로 둡니다. 임의의 점수 하나로 호환성·캐시·용량을 섞지 않습니다.

## 4. 제안하는 실행 순서

```text
논리 모델 이름으로 요청 수신
  -> 기능·대화 길이·이전 가능성으로 후보 제외
  -> 인증 상태·소진·대기·동시 실행 한도 검사
  -> 현재 대화의 계정이 사용 가능하면 유지
  -> 같은 모델의 다른 독립 사용량 영역 선택
  -> 허용된 다른 모델 후보 선택
  -> 실행 용량 예약
  -> 제공자에 맞게 요청 준비 및 전송
  -> 사용량·오류·캐시 관측 갱신과 예약 해제
  -> 전환했다면 새 계정에 대화 재고정
```

논리 모델은 `coding-primary`, `coding-fast`, `reasoning`처럼 작업을 표현합니다. 실제 후보는 반드시 `(provider, model, account pool)`로 지정합니다. “GPT”는 모델 계열이며 Command Code·Devin은 전송 경로/구독 제공자이므로 동일한 분류로 저장하지 않습니다. 중간 서비스에서 같은 이름의 모델을 제공해도 캐시·기능이 같다는 증거는 별도로 필요합니다.

### 사용량 상태

사용량은 단일 `remaining_tokens` 숫자로 만들지 않습니다.

- 인증 신원과 사용량 공유 영역을 별도 식별합니다.
- 5시간·주간·월간·모델별 제한을 각각 보존합니다.
- 잔액, 요청 수, 토큰 수, 사용률은 단위를 보존합니다.
- 관측 시각, 출처, 초기화 시각, 알려짐 여부를 붙입니다.
- 응답 헤더의 관측과 별도 조회를 공통 상태에 게시합니다.
- 오래되거나 조회 실패한 값은 “알 수 없음”이지 0도 무제한도 아닙니다.
- 단기 속도 제한과 구독 소진을 구별합니다. 소진은 알려진 초기화까지 제외하고 불명확한 오류는 제한된 대기 후 한 실행만 시험합니다.

권장 갱신은 응답마다 수동 관측을 반영하고, 별도 조회는 백그라운드에서 합쳐 실행하는 것입니다. 매 요청마다 외부 사용량 조회를 기다리게 하지 않습니다. 소진 직전·초기화 직후·실패 발생 때만 추가 확인합니다.

예약은 정확한 구독 소모량을 안다는 뜻이 아닙니다. 모델별 제한 단위를 실제로 알 때만 추정 토큰을 차감하고, 불명확한 구독은 동시 실행 슬롯으로 과배정을 제한합니다. 취소·실패에도 예약을 반환하고 뒤늦은 응답이 새로운 소진 상태를 덮어쓰지 않게 세대를 구별합니다.

### 대화와 캐시는 분리

1. **대화 기록**은 사용자 발언, 도구 호출과 결과, 작업 목표를 보존하는 자료입니다.
2. **제공자 프롬프트 캐시**는 입력 접두부 계산을 재사용하는 내부 상태입니다.
3. **응답 캐시**는 과거 답변을 다시 반환합니다. 실시간 파일·도구 작업에는 기본적으로 사용하지 않습니다.

[OpenAI 공식 문서](https://platform.openai.com/docs/guides/prompt-caching)는 접두부 일치와 실제 머신 배정이 필요하며 조직·지역 사이에 캐시가 공유되지 않는다고 설명합니다. 캐시 키는 모든 모델에서 같은 효과를 내지 않으며 캐시 적중을 보장하지 않습니다.

[Claude 공식 문서](https://platform.claude.com/docs/en/build-with-claude/prompt-caching)는 tools, system, messages 순서의 접두부와 캐시 경계, 수명, 실제 읽기·쓰기 토큰을 설명합니다. 고정 지침·도구 정의를 앞에 두고 변화하는 자료를 뒤에 붙이며 과거 대화를 매번 다시 쓰지 않는 것이 공통 원칙입니다.

두 문서는 공식 API의 근거입니다. 구독용 비공식 전송 경로에 같은 과금·사용량 절감률을 적용하지 않습니다. 캐시가 빨라진다는 사실과 구독 잔액이 덜 줄어든다는 사실은 별도로 측정해야 합니다.

완전한 대화 입력이 매번 오는 클라이언트에는 별도 전체 대화 저장소가 필요하지 않습니다. 기존 세션 매칭을 활용합니다. 서버측 응답 ID만 오는 요청까지 다른 계정에 넘기려면 원문 기록을 복원하는 별도 상태 계층이 필요합니다. 로깅 파일을 대화 데이터베이스처럼 사용하지 않습니다.

암호화 사고 내용, 제공자측 응답 ID·파일 ID는 다른 계정에 그대로 재전송하지 않습니다. 해당 경로에서 복원 가능한 원문이 없으면 재전송이 필요하다는 구조화 오류로 끝내고 클라이언트가 전체 대화를 다시 보내게 합니다. 요약은 원문과 동일한 상태가 아니므로 손실을 숨기지 않습니다.

### 실패와 전환 경계

- 토큰 만료는 갱신을 먼저 시도하고 재인증 필요 상태면 해당 계정을 제외합니다.
- 계정 소진은 같은 모델의 다른 독립 사용량 영역을 먼저 선택합니다.
- 기능·대화 길이 불일치는 호환 후보를 선택합니다. 도구 결과를 일반 문장으로 바꿔 기능이 보존됐다고 취급하지 않습니다.
- 잘못된 요청은 그대로 오류를 반환합니다.
- 응답이 아직 외부로 전달되지 않았다면 재시도할 수 있습니다.
- 이미 텍스트·도구 호출이 전달된 뒤에는 다른 모델의 출력을 같은 응답에 이어 붙이지 않습니다. 부분 실패를 표시하고 다음 실행 경계에서 복구합니다.
- 도구 호출이 실제 실행됐을 수 있으면 같은 작업을 무조건 반복하지 않습니다. 호출 ID와 실행 확인 상태를 보존하고 클라이언트의 복구 절차와 맞춥니다.

## 5. 구현 순서 제안

1. **공통 사용량 관측 연결**. Command Code·Devin을 포함한 조회와 응답 관측을 서버가 소비하는 같은 자료 구조에 게시합니다. 먼저 “이미 소진된 계정 제외”를 완성합니다.
2. **명시적 대체 프로필**. 제공자·모델 후보, 필수 기능, 같은 모델 우선 전환, 유료 추가 사용 허용 여부를 설정합니다. 기존 Go 호환 설정을 바꾸지 않고 Rust 확장으로 구분합니다.
3. **세션 고정과 이전 판정**. 기존 affinity/LCP를 재사용하고 서버측 상태가 있는 요청의 계정 변경을 검사합니다. 전환 이후 재고정합니다.
4. **예약과 복구 시험**. 계정/사용량 영역별 동시 실행 제한과 초기화 후 단일 시험 실행을 연결합니다. 멀티 인스턴스 공유는 나중 단계입니다.
5. **관측 화면**. 왜 이 계정을 골랐는지, 사용량 자료가 언제 관측됐는지, 무엇 때문에 전환했는지 표시합니다. 도구·키·본문은 선택 기록에 담지 않습니다.

완료 검증에는 소진 계정 건너뛰기, 같은 사용량 영역의 키 중복 계산 방지, 오래된 사용량, 초기화 후 단일 시험, 동시 요청 과배정, 스트림 초기/중간 실패, 도구 실행 중복 방지, 서버측 ID 이전 차단, 취소 후 예약 해제를 포함합니다. 모든 실행 검증은 로컬 모의 제공자로 수행합니다.

관측 지표는 대화당 전환 횟수, 전환 성공률, 출력 시작까지 시간, 제공자가 보고한 캐시 읽기/쓰기 토큰, 사용량 자료의 나이, 제한 오류율입니다. 내부 추정량과 제공자 실제 관측값은 별도로 표시합니다.

선택한 소스 범위의 비교이며 모든 게이트웨이의 전수 조사나 성능 측정이 아닙니다. 외부 문서의 긴 응답은 필요한 절을 읽었으며 잘린 뒷부분을 검증한 것으로 취급하지 않았습니다. 참조 구현의 선언·코드는 확인했지만 실제 제공자 계정으로 실행하지 않았고 테스트도 실행하지 않았습니다. 운영 코드 변경이 없는 조사입니다.

보조 조사 두 건은 `insufficient credits to make this request` 오류로 시작되지 않아 직접 조사했습니다. ego-browser 공간 2는 종료 완료를 확인했습니다. 추가 구현은 이 설계의 범위를 정한 뒤 진행할 수 있습니다.
